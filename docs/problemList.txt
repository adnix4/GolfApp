## Deployment path — real-world pilot (2026-07-09)
Goal: deploy Golf Fundraiser Pro for a real-world test event. Ordered phases;
mark [x] as completed. D1 items have external lead times — start them first,
they run in parallel with everything else.

[ ] D1. DECISIONS & ACCOUNTS (user actions; longest lead times)

          works), web on Vercel, admin as a static expo export served
          anywhere, managed Postgres+PostGIS and Redis. A single VPS with
          docker-compose + reverse proxy is also fine at pilot scale.

          app. subdomains).

[x] D8. LET CHECKED-IN GOLFERS BID WITHOUT A SAVED CARD (added 2026-07-31,
        done 2026-07-31)
        DONE — but the job was bigger than first scoped. Three defects, not
        one, stood between a checked-in golfer and a cardless bid:
        (a) Admin's Check In button was DEAD CODE. The API projects
            CheckInStatus with .ToString() ("Pending"/"CheckedIn"/"Complete")
            but both screens compared against lowercase, so the button never
            rendered, the pill was always grey, and every team counted as
            checked in. Fixed via apps/admin/src/lib/checkIn.ts (single source
            of truth for the wire format) + packages/ui TeamCard, which had the
            same bug. shared-types' CheckInStatus union now matches the wire.
        (b) NOTHING checked in a GOLFER. Admin only called the team endpoint,
            and TeamService.CheckInTeamAsync set only team.CheckInStatus — it
            never touched Player.CheckInStatus and emitted no SignalR. It now
            cascades to every golfer on the roster, sets the team to Complete,
            and broadcasts. PlayerService.CheckInAsync is now idempotent (it
            threw), matching what its own endpoint doc already claimed.
        (c) The mobile client was STRICTER THAN THE SERVER: auction.tsx disabled
            the Bid/Pledge button on !hasPaymentMethod alone, ignoring check-in,
            and the banner claimed "bids require a saved card" — false for a
            checked-in golfer. Both now carry the check-in condition, and the
            banner reads "You're checked in — no card needed to bid."
        UI (as specified by the user): a "Check In Team" button that appears
        ONLY when every golfer on the roster has a card, replaced otherwise by
        "N of M golfers have no card — check in individually"; a per-golfer
        Check In button on every roster row; and a confirm popup that states
        card status either way — the cardless variant warns that a winner must
        be collected from manually. Copy is single-sourced in checkIn.ts.
        PLUMBING: PlayerResponse gained HasPaymentMethod (and the two divergent
        MapToPlayerResponse copies were merged into one — PlayerService's had
        already drifted, silently dropping the entry-fee columns).
        PlayerCacheDto gained IsCheckedIn. GET /pub/events/{code}/status now
        returns the caller's own {isCheckedIn, hasPaymentMethod} when the
        X-GFP-Player-Id / X-GFP-Session-Token headers are presented (fail-closed
        to null) — mobile's session poll already ran every tick, so this costs
        zero extra requests and is what unlocks the button after check-in.
        The rule itself is now shared: packages/shared-types/src/auctionRules.ts
        mirrors AuctionBidRules.NeedsPaymentMethod, tested against the same
        three cases as apps/api-tests/AuctionBidRulesTests.cs.
        COLLECTION CONSEQUENCE (the standing decision behind this item): a
        cardless winner cannot be charged. ChargeWinnerAsync throws, the winner
        is marked ChargeStatus.Failed and logged, and the item close still
        completes — nothing breaks. The organizer settles via the failed-charge
        flow (waive / retry / collect at the table), the same cash fallback D1
        already assumes for entry fees. Confirm the organizer is willing to
        chase payment before enabling this for a real event.
        VERIFIED: 450 API tests, 119 admin, 115 mobile, 91 shared-types, 4 apps
        typecheck clean. Driven live against localhost — team cascade, per-golfer
        promotion to Complete, idempotency, the status-poll flip, the join
        payload, and both bid outcomes (cardless+CheckedIn -> 200,
        cardless+Pending -> 400 NO_PAYMENT_METHOD). Admin UI clicked through in
        a browser: both popup variants and the team cascade confirmed against
        the DB. NOT visually exercised: the mobile auction screen itself
        (apps/mobile has no RN component-test harness and vitest only picks up
        src/**/*.ts) — its inputs and rule are unit-tested instead.
        D4 note: the dress-rehearsal sub-item "bid from a phone with no saved
        card after check-in" is now pre-verified at the API level; only the
        on-device walk and the failed-charge resolution remain for D4.

[x] D9. OPEN-SCORING GATE + THE AUCTION OUTLIVES THE ROUND (2026-07-31)
        Started as "don't enable Open Scoring until all teams are checked in".
        That gate is done — Overview greys the button, shows "N of M teams still
        need check-in", and offers "Open Scoring anyway" behind a confirm naming
        the outstanding teams, so a no-show foursome can't strand the round. The
        gate is an admin affordance only; ValidateStatusTransition is unchanged.
        Counted in TEAMS off counts.teamsCheckedIn (CheckedIn||Complete), which
        was already on the page — no new request on the normal path.
        THE BIGGER FIND: the event status machine assumed a golf-only day ending
        at Completed, but a fundraiser runs on into a banquet. The auction API,
        the close job and the admin auction UI have ZERO EventStatus coupling —
        the conflation was entirely in the clients. Fixed without a new status
        or a migration:
          - check-in now allowed in Active OR Scoring (EventStatusRules
            .CheckInAllowed) so late arrivals can still be checked in — which
            also keeps them eligible to bid under the D8 waiver. Completed and
            Cancelled stay closed.
          - /join no longer refuses Completed; the event picker lists a Completed
            event only while it still has an Open/Extended auction item, so the
            public directory doesn't accumulate finished events.
          - the mobile shell no longer hides every tab at Completed (it showed an
            "Event Ended" wall with no way past, trapping golfers mid-auction).
            Scoring closes; auction and leaderboard stay reachable.
          - new POST /events/{id}/auction/sessions/end + "End Auction" button —
            the organizer's "auction is over" signal. Previously IsActive only
            flipped when the NEXT session started, so a finished auction stayed
            "in progress" on every attendee screen. This is the second
            completion state, without touching the event status machine.
        GUESTS (non-golfers who only want to bid): new RegistrationType.Attendee
        — a team-less Player, not a new entity, because bids.player_id /
        auction_winners.player_id / stripe_customers.player_id are all
        non-nullable FKs to players. No migration (registration_type is a string
        column, team_id already nullable). Being team-less keeps them off the
        leaderboard, out of pairings, out of team capacity and out of the
        check-in counts that gate Open Scoring. Admin: "Guest — not playing"
        toggle on the Walk-Up form plus a Guests section on Registration (they
        appear on no roster, so without it they could never be checked in).
        They may be added after the round; golfers may not. Mobile: a guest goes
        straight in (the old free-agent path threw the session token away at
        join.tsx) with the scorecard and team tabs hidden.
        ALSO FIXED: auction.tsx dropped Extended items from the golfer's list, so
        an item that extended on a last-30-second bid vanished at its hottest
        moment; and registration.tsx rendered Check In buttons after the event
        left Active (a D8 regression) which 400d.
        VERIFIED: 459 API / 130 admin / 115 mobile / 91 shared-types tests, four
        apps typecheck. Driven live: gate blocked -> override dialog names the 5
        outstanding teams -> cancel leaves it Active -> all checked in -> button
        enables. Late check-in during Scoring 200s (400d before). After
        Completed: golfer join 200s, guest joins straight in, cardless checked-in
        guest bids 200, guest add 201 / golfer add 400, end-session 204 then 200.
        NOT visually exercised: the mobile screens (no RN component-test harness).

[ ] D10. COLLECT PAYMENT INFO AT CHECK-IN — BLOCKED ON D1 (STRIPE ACTIVATION)
        Asked 2026-07-31; deferred deliberately, not for lack of time.
        It cannot be built OR dress-rehearsed before Stripe is live:
        CreateSetupIntentAsync (PaymentsService.cs:29) has no IsUsableStripeKey
        guard — it sets the key at :40 and immediately calls Stripe's
        CustomerService at :52, so the shipped sk_test_REPLACE_WITH… placeholder
        raises an unhandled StripeException (401), not a graceful 400.
        IsUsableStripeKey (:305) guards ONLY donations. Unlike the entry-fee path
        (A8 swallow-and-return-null at TeamService.cs:943-959 → "pay at
        check-in"), the card-on-file flow has NO degraded mode at all.
        NOTE THE INTENDED DESIGN IS NOT A WORKER TYPING A CARD. TechSpec:604:
        "organizer shares a short URL or QR that opens a Stripe-hosted card entry
        page on the attendee's phone at check-in" — the existing per-player QR
        machinery (QrService, QrType.PlayerCheckin, GET /pub/qr/scan) could carry
        that, with no PCI exposure and no staff handling cards.
        Both current endpoints are gated on the golfer's /join session token
        (PaymentsService.cs:37,85), which admin never receives and which is null
        for exactly the golfers a worker would be helping, so staff-authorized
        variants need designing against a live account.
        Until then the fallbacks hold: cash entry fees via markFeePaid, and
        check-in waiving the auction card requirement (D8) with re-charge/waive.

[x] D12. NO ITEM COULD BE BID ON, AND THE FAILURE WAS INVISIBLE (found 2026-07-31,
        fixed same day). Reported as "a checked-in golfer taps Bid and nothing
        happens". Check-in (D8) was fine; two unrelated defects compounded:
        - The bid modal quoted currentHighBidCents + bidIncrementCents as the
          minimum, while the server uses Max(startingBidCents, high + increment)
          (AuctionBidRules.MinimumRequired). On any item with no bids yet — all 8
          in St. Mark Classic — it advertised $5.00 for a $50.00 item, so a bid at
          the quoted figure came back 400 BID_TOO_LOW. Same client/server drift
          that caused D8; MinimumRequired now mirrors into shared-types
          (minimumBidCents) beside needsPaymentMethod, tested case-for-case
          against AuctionBidRulesTests.
        - react-native-web ships Alert as a literal no-op (`class Alert { static
          alert() {} }`), so on the web build EVERY Alert.alert in the app went
          nowhere — hence "no warning". Replaced by src/lib/notify.ts (real
          dialog on native, window.alert/confirm on web) across auction,
          payment-setup and edit-profile; the bid modal additionally shows its
          error inline under the amount field. Server codes are now translated
          for humans — golfers were being shown the string "BID_TOO_LOW:5000".
        Anything new that reports to the golfer must use notify(), not Alert.

[x] D13. REGISTRATION AND FUNDRAISING DISAGREED ON WHO PAID (found 2026-07-31,
        fixed same day). St. Mark Classic: Fundraising said "14 of 19 golfers
        paid", Registration showed every team "✓ Fees Paid". Both read the same
        rows; the team-level view OR-ed in the legacy teams.entry_fee_paid flag:
          EntryFeePaid = team.EntryFeePaid || all-players-paid
        which is sticky — once true the roster reads as paid no matter what the
        golfers paid. Phase14's own migration note already said the flag is
        "retained for now but no longer read". Two ways it went wrong:
          - Phase14 added players.entry_fee_paid_cents at default 0 and
            backfilled nothing, so every team marked paid before 2026-07-06
            carries a true flag over a wholly unpaid roster (kim's slashers).
          - A golfer assigned to an already-paid team pays nothing and is not
            marked, but the flag kept the team reading as paid (Sleepers 3/4).
            Correct behaviour is that the team stops being fully paid and the
            organizer gets Mark All Paid back — that is what dropping the flag
            gives, so no separate cascade is wanted.
        Fixed in TeamService.MapToTeamResponse AND EventService.GetFundraisingAsync
        (teamsPaid had the identical OR). The flag is still written for
        continuity but is now read nowhere. Registration also shows the "0/N
        paid" pill it used to hide at zero.
        Entry-fee state lives on the golfer. Do not reintroduce a team-level
        boolean as a source of truth.

[ ] D14. FUND-A-NEED ITEMS ALWAYS REPORT "RAISED: $0.00" (found 2026-07-31)
        AuctionService.MapItem (:768) sets TotalRaisedCents = i.CurrentHighBidCents,
        but PlaceBidAsync only writes CurrentHighBidCents for competitive items
        ("if (!isDonation)", :268) — pledges stack rather than outbid, so the
        column stays 0 on a donation item forever. Every Fund-a-Need item in the
        mobile auction list therefore shows "Raised: $0.00 / $goal" no matter how
        much has been pledged, which is exactly the number that motivates the
        next pledge. GoalCents is served but the progress against it is a lie.
        Fix: sum the item's bids for donation types. The same reasoning is
        already written out in EventService.GetAuctionRevenueAsync (D-auction
        total), which sums bids for precisely this reason — so the query shape
        is settled, it just needs to reach the DTO. Watch the N+1: MapItem is
        called per item from GetPublicItemsAsync, so the sums want one grouped
        query up front, not a lookup inside the map.
        Small, self-contained, and golfer-visible. Good candidate before pilot.

[ ] D15. A GOLFER WITHOUT A TEAM NEVER LEARNS THEY WERE CHECKED IN (found
        2026-07-31). session.tsx:74 gates the whole foreground poll on
        `!session.team` — it returns early for any golfer with no team. That poll
        is the only thing that refreshes isCheckedIn (and the event theme and
        sponsor list) after /join. So a guest or an unassigned free agent who is
        checked in at the desk keeps a stale session: the auction bid button
        stays locked behind "add a card", and the D8 waiver they are entitled to
        never reaches the device. Rejoining is the only workaround.
        Real today: St. Mark Classic (walk) has two such golfers (Hank Sponsor,
        Gina Guest). The gate exists because the body below it syncs scores and
        dereferences session.team!, so the fix is to split the effect — run the
        status/check-in/theme poll for every session, and keep the score-sync
        half gated on a team.

[ ] D16. "MARK ALL PAID" DOES NOTHING ON A FREE EVENT (found 2026-07-31)
        MarkTeamPlayersPaid reads `ReadEntryFeeFromConfig(...) ?? 0` and writes
        that to every golfer, so with no entryFeeCents configured it records 0 —
        which every reader treats as unpaid. The team stays "0/N paid" and the
        button never resolves. Latent before D13 (the legacy team flag made the
        team read as paid regardless); D13 removed that mask, so this is now
        visible. Note the admin registration screen never consults the event's
        entryFeeCents at all, so it shows fee UI on events that have no fee.
        Fix is a product decision, not just code: either hide the fee row when
        entryFeeCents is null/0 (nothing to collect), or treat a free event as
        paid by definition. Prefer the former — a free event has no fee state
        worth showing. EventDetail already carries entryFeeCents (admin api.ts
        :314), so the screen has what it needs.
