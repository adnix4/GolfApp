# Problem List

## Deployment path — real-world pilot (2026-07-09)
Goal: deploy Golf Fundraiser Pro for a real-world test event. Ordered phases;
mark [x] as completed. D1 items have external lead times — start them first,
they run in parallel with everything else.

[ ] D1. DECISIONS & ACCOUNTS (user actions; longest lead times)
        - Hosting choice. Spec default: API on Railway (any container host
          works), web on Vercel, admin as a static expo export served
          anywhere, managed Postgres+PostGIS and Redis. A single VPS with
          docker-compose + reverse proxy is also fine at pilot scale.
        - Domain + DNS (.env.example assumes golffundraiser.pro with api. and
          app. subdomains).
        - Apple Developer Program enrollment ($99/yr; TestFlight review adds
          days). SDK 56 constraint: shipped iOS builds require iOS 16.4+
          (Xcode 26.4 — EAS cloud runners handle it, Windows dev unaffected,
          but older devices are dropped). Confirm EAS image + minimum-OS
          commitment before releasing a build.
        - Stripe live account activation (business verification lead time) —
          or run the pilot in test mode and use the cash mark-paid-at-check-in
          path for real fees.
        - Email provider (SendGrid or similar) + SPF/DKIM domain auth.
          CRITICAL PATH: join email-verification codes must actually arrive
          once the dev bypass code is off (see A3 history in git).

[ ] D2. CODE HARDENING (no infra needed; can be done now)
        - Startup guard: refuse to boot in Production when
          JoinVerification:TestBypassCode is set (converts the "999999 must
          never reach production" note into a can't).
        - ForwardedHeaders configuration so the rate limiter and the
          IP-keyed security policies (auth/join/donate) see real client IPs
          behind the reverse proxy — the code comments already flag this.
        - DataProtection key persistence to a mounted volume/store so keys
          survive container restarts (currently Windows DPAPI locally).
        - Production CORS origins from configuration.
        - /health endpoint for host health checks (verify one exists).
        - Migration story: auto-migrate is Development-only by design, so
          deploys need an explicit `dotnet ef database update` step or an
          opt-in migrate-on-startup flag for production.
        - DEPLOYMENT.md: complete env-var checklist (extend .env.example's
          STAGING/PROD annotations) + deploy runbook per app.

[ ] D3. STAGING ENVIRONMENT (after D1 hosting/domain decided)

[ ] D4. DRESS REHEARSAL on staging (the pilot succeeds or fails here)

[ ] D7. APP STORE LINKS — FINISH WHEN THE APP GOES LIVE (added 2026-07-31)
        The web app already has the "Get the App" UI in place; it is running in
        a deliberate pre-launch mode until the store listings exist.
        Current behavior: the post-registration success modal shows a "Get the
        App" button (AppPromo in
        apps/web/src/app/e/[orgSlug]/[eventCode]/EventActions.tsx). Because
        NEXT_PUBLIC_IOS_APP_URL / NEXT_PUBLIC_ANDROID_APP_URL are unset, it
        opens a "Coming Soon" dialog instead of a store.
        TO FINISH once the app is published:
        - Set NEXT_PUBLIC_IOS_APP_URL and NEXT_PUBLIC_ANDROID_APP_URL in the
          web deployment env (documented in .env.example). Setting them is the
          ONLY step — no code change is needed. With them set the button sends
          iOS/Android phones straight to their store and shows a two-button
          store chooser on desktop; the Coming Soon copy disappears by itself.
        - Set them per environment: staging can point at TestFlight / the
          Play internal-testing link before the public listings go live.
        - The same two vars also drive SmartJoin
          (apps/web/src/app/e/[orgSlug]/[eventCode]/join/SmartJoin.tsx), which
          hands a golfer off to the store when the gfp:// deep link finds no
          installed app — verify that path at the same time.
        - Re-check the Coming Soon fallback still reads correctly if only ONE
          platform ships first (e.g. Android live, iOS still in review): the
          chooser shows just the live store, which is intended.

[ ] D8. LET CHECKED-IN GOLFERS BID WITHOUT A SAVED CARD (added 2026-07-31)
        Pilot-prep item. Removes the hard dependency on Stripe activation for
        the auction, which has business-verification lead time (see D1).
        THE SERVER ALREADY ALLOWS THIS. AuctionBidRules.cs:
          NeedsPaymentMethod = !hasPaymentMethod && checkInStatus != CheckedIn
        i.e. checking a golfer in already waives the saved-card requirement.
        /seed-demo-event relies on exactly this to seed bids with no Stripe key.
        THE MOBILE APP IS STRICTER THAN THE SERVER and must be brought in line:
        - apps/mobile/app/(scoring)/auction.tsx line ~483 disables the Bid/Pledge
          button on `!player?.hasPaymentMethod` alone, ignoring check-in; the
          banner at line ~198 says "bids require a saved card", which is simply
          FALSE for a checked-in golfer. Both need the check-in condition.
        - API CHANGE NEEDED FIRST: PlayerCacheDto (Features/Mobile/MobileModels.cs)
          exposes HasPaymentMethod but NOT CheckInStatus, and the mobile app has
          no notion of check-in state anywhere. Add the field to the join payload
          (and refresh it on check-in) before the client rule can be written —
          this is NOT a client-only change.
        - Re-word the banner to something true, e.g. "Add a card to bid before
          you check in" / "You're checked in — no card needed to bid."
        COLLECTION CONSEQUENCE (the real decision): a cardless winner cannot be
        charged. ChargeWinnerAsync throws, the winner is marked
        ChargeStatus.Failed and logged, and the item close still completes
        (AuctionService.cs ~458-465) — nothing breaks. The organizer then settles
        via the existing failed-charge flow (WaiveChargeAsync / retry / collect
        at the table). That is the same cash fallback D1 already assumes for
        entry fees, so it is consistent — but confirm the organizer is willing to
        chase payment before enabling this for a real event.
        VERIFY AT D4 (dress rehearsal): bid from a phone with no card saved after
        check-in, close the item, and walk the failed-charge resolution in admin.
