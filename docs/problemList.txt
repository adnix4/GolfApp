## Standing rules (extracted 2026-08-15)
Completed entries below were compressed to one line each. These are the durable
decisions that came out of them — the parts that govern code not yet written.
Breaking one of these re-opens a bug that was already paid for. Each names the
entry it came from; the full reasoning is in git history for that entry.

- ENTRY-FEE STATE LIVES ON THE GOLFER (D13). Never reintroduce a team-level
  paid boolean as a source of truth. teams.entry_fee_paid is still written for
  continuity and read nowhere.
- USE notify(), NOT Alert (D12). react-native-web ships Alert as a literal
  no-op, so every Alert.alert on the web build goes nowhere. Anything that
  reports to a golfer goes through src/lib/notify.ts.
- PROXY BIDDING IS SILENT ITEMS ONLY (U4). Do not widen it. A Live lot is
  called aloud by an auctioneer and Fund-a-Need pledges stack rather than
  compete. The proxy step is the item's bid_increment_cents, not a flat $1.
- STARTING HOLES ARE ASSIGNED ON StartType == Shotgun ONLY (U5), never by
  Format == Scramble. A scramble on tee times starts everyone at hole 1;
  stamping holes there makes the scorecard lie. Settled — do not widen.
- CHECK-IN IS ALLOWED IN Active OR Scoring (D9), so late arrivals stay
  eligible to bid under the D8 waiver. Completed and Cancelled stay closed.
- A CARDLESS WINNER CANNOT BE CHARGED (D8). The charge fails, the winner is
  marked ChargeStatus.Failed, and the item still closes. The organizer settles
  by hand. Confirm they will chase payment before enabling this for a real event.
- CLIENT AND SERVER BID RULES MOVE TOGETHER (D12, U4, U7m).
  packages/shared-types/src/auctionRules.ts mirrors AuctionBidRules; the
  lockstep comment at its head names the server file to change with it.
- A ROTATED REFRESH TOKEN IS REPLAYABLE FOR 30s (D17), knowingly traded to stop
  concurrent-refresh logouts. Reuse outside the window logs "Possible token
  theft" — wire that into D6's monitoring.
- /health DOES NOT PROBE DB OR REDIS (D2). It answers "the process is up", not
  "the API can serve". If D6 wants dependency health, that is a new task.
- TESTING THE PRODUCTION STARTUP GUARDS: `dotnet run` applies
  Properties/launchSettings.json, which pins ASPNETCORE_ENVIRONMENT=Development
  and silently masks them (D2). Use --no-launch-profile.

[x] D22. QR SCORECARD TRANSFER IS BROKEN, AND ITS SIGNATURE CAN'T STOP FORGERY (2026-10-05)
        Found while writing unit tests for it (docs/TestingToDoList.txt TT1).
        QR transfer is the runbook's fallback when a team had no signal: the
        phone shows its scorecard as a QR code, the desk scans it on QR Import.
        (1) BROKEN: the phone and the API sign differently.
            Phone, apps/mobile/app/(round-end)/qr-transfer.tsx:70:
              key = eventCode + teamId; message = JSON.stringify(payload)
            API, apps/api/Features/Scores/ScoreService.cs:489-490:
              key = "{eventCode}:{teamId}";
              message = "v|ec|tid|did|ts|<scores, compact, by hole>"
            Also: missing putts are "p":null on the phone but omitted on the
            server. VERIFIED 2026-10-05 with a throwaway test through the real
            QrCollectAsync: a payload built exactly as the phone builds it is
            REJECTED ("QR signature is invalid… may have been tampered with");
            one built the server's way is accepted. So every real QR import
            fails. The Phase 2 spec gives the key (event_code + team_id, no
            colon) but never defines the message, which is how the two drifted.
            No test on either side, and nothing checks one against the other.
        (2) FORGEABLE: the key is built from the event code (shared with every
            golfer) and the team id (public: leaderboard and join responses).
            Anyone can sign any scores they like, so the check catches
            corruption, not tampering, despite its error message. A golfer
            could show the desk a crafted QR with better scores.
        DECISION NEEDED: fix (1) by making both sides agree on one documented
        format, with a shared test vector run on both sides. For (2), the
        golfer's /join session token is a per-golfer secret the phone and the
        server both hold; keying the HMAC with it would make the signature
        real. That changes the phone and the API together.
        Related, smaller (QrService player check-in token, which IS keyed with
        the server secret): it compares signatures with != instead of a
        constant-time compare, and its base64 decode always appends "==",
        which only works because the payload length never changes.
        FIXED 2026-10-05. USER DECISION: no signature. Golfers enter their own
        scores, so the QR only has to carry them reliably between the phone and
        the server; security is not the goal (and the old key was public anyway).
        - Phone: the builder moved to apps/mobile/src/lib/qrPayload.ts; no HMAC,
          so no dependency on Web Crypto (crypto.subtle, which Hermes likely
          lacks). Format v1: Base64 (UTF-8) JSON
          { v, ec, tid, tn, did, ts, part?, total?, scores:[{h,g,p}] }.
        - API: QrCollectAsync no longer checks a signature; a leftover "sig" is
          ignored. Every structural check stays (Base64, JSON, version, event
          code, team in event, event status, hole and score ranges, conflicts).
        - CONTRACT: apps/api-tests/Fixtures/qr-payload-v1.txt is written by the
          phone's real builder. The mobile test checks the builder still
          produces it byte for byte; the API test imports it. VERIFIED: renaming
          a field on either side fails a test.
        - e2e "QR scorecard transfer": the two-part fixture, re-targeted at the
          run's event, imports 6 holes on real Postgres and scores +3 thru 6.
        Supersedes the Phase 2 spec line "signs with HMAC-SHA256" (the spec file
        is not edited). The check-in token issues above are TestingToDoList TT12.

  [ ] U6. (OPEN, added 2026-08-03) EVALUATE BUY-IT-NOW. Not a reported bug —
        raised while adding the mobile bid-confirmation dialog (2026-08-03),
        which had to warn about this and made the design worth a decision.
        HOW IT WORKS TODAY. AuctionBidRules.IsBuyNow is `amount >= buyNowPrice`,
        evaluated in PlaceBidAsync for EVERY auction type, and it closes the item
        on the spot. The separate POST /auction/items/{id}/buy-now route is
        cosmetic — BidController.BuyNow calls the same PlaceBidAsync, so nothing
        distinguishes "I meant to buy it" from "I typed a big number".
        WHY THAT COLLIDES WITH U4. On a Silent lot the amount submitted is a
        PRIVATE MAXIMUM the server spends on the golfer's behalf. The ceiling and
        the purchase trigger are therefore the same number: a golfer who sets a
        deliberately generous max to stop being outbid all night crosses the
        buy-now price and buys the lot outright instead. Those are opposite
        intents expressed by one field.
        FOUR QUESTIONS TO DECIDE:
        (a) Should a proxy maximum be able to trigger buy-now at all, or should
            buying require an explicit action (its own button, priced at the
            posted figure) with the max capped below it?
        (b) The price billed is inconsistent. A proxy buy-now bills
            BuyNowPriceCents (AuctionService.cs:301-303, deliberate — the
            ceiling must never be charged). A LIVE buy-now falls through to
            `CurrentHighBidCents = Math.Max(current, amount)`, so a golfer who
            types more than the posted price PAYS more than the posted price.
            Same act, two prices; pick one.
        (c) IsBuyNow is evaluated unconditionally, so a Fund-a-Need item with a
            buy-now price set CLOSES on a large enough pledge — ending the
            "everyone pledges" item because someone was generous. Probably wants
            to be excluded outright, the way donations are excluded from proxy.
        (d) The golfer cannot see the price they might trip over. The admin item
            form offers a buy-now field (admin auction.tsx:484), but mobile only
            carries buyNowPriceCents in the DTO (mobile api.ts:379) — no screen
            renders it. The bid modal should show it, not just the confirmation
            dialog after the fact.
        MITIGATION ALREADY SHIPPED, so this is not urgent: the confirmation
        dialog names the buy-now price, says the bidding ends now, quotes the
        figure that will actually be billed, and tells the golfer what to enter
