## The evaluation (2026-10-05)

### Method
- API: coverlet over all 727 xUnit tests, summarised by area and by file
  (scripts/coverage-summary.js plus a per-file pass), EF migrations excluded.
- JS: for every logic module (lib/, src/*.ts, lib/*.tsx) in each workspace,
  checked whether any test imports it.
- Quality: scanned every suite for skipped/focused tests, tests with fewer
  assertions than cases, real sleeps, and wall-clock dependence; read the
  payments tests against the service's methods.

### Numbers
- API: 727 tests, all passing. Line coverage 51.6% excluding migrations
  (6,880 of 13,324 lines; 9,266 migration lines excluded).
  After TT2/TT3 (2026-10-05): 790 tests, 54.3%.
- JS: about 644 tests. apps/mobile 215 (10k source lines), apps/admin 198
  (18k), packages/shared-types 163, packages/theme 42, apps/web 20,
  packages/ui 6.

### What's in good shape
- No skipped or focused tests anywhere; no sleeps in C#; every JS test file
  has at least as many assertions as test cases; the C# suite averages about
  1.9 assertions per test.
- Core logic is tested directly: scoring formats, event status machine, bid
  rules and proxy bidding, score conflict rules, the league engines
  (handicap, pairing, standings, skins), rate-limit keys, the golfer
  session-token check.
- Authorization is tested deliberately ("wrong token", "other org", "other
  event") across payments, push tokens, staff invites and password reset.
- Recent tests were checked by breaking the code on purpose and watching them
  fail.
- EF InMemory can't do transactions, row locks or real migrations; the e2e job
  covers those against real Postgres in CI.

### Why Payments is low
The guard paths are well tested. The happy paths call Stripe's SDK, which the
code constructs directly (`new PaymentIntentService()` and similar, 10 places),
so nothing can stand in for Stripe in a unit test. ApplyEntryFeePaymentAsync is
unit-tested; ApplyDonationPaymentAsync is covered only by the e2e webhook
phase.
